# Design Checklist

This document closes the system: it states, in one place, what the Care Ecosystem's design language is *for* (the philosophy) and how to verify any given screen actually honors it (the checklist). Nothing should ship — as a Figma file, a PR, or an AI-generated screen — without passing through this document.

---

## Part 1: Final Deliverables — The Care Ecosystem Design Philosophy

These nine statements are the distillation of every other document in `docs/design/`. If a decision isn't clearly answered by a specific document, it should be answered by one of these.

### 1. Care Ecosystem Design Philosophy

We design calm, competent software for people doing serious work: running a health business, or finding care for themselves or someone they love. The product should never be the hard part. Every design decision is judged against one question — does this make a real task easier, faster, or safer — not against whether it looks impressive in isolation. Restraint is a design choice, not an absence of one (`DESIGN_VISION.md`, `DESIGN_PRINCIPLES.md`).

### 2. UI Philosophy

Hierarchy comes from typography, spacing, and color first — decoration (shadows, gradients, borders) is a last resort, used only when the first three genuinely can't carry the distinction alone (`DESIGN_PRINCIPLES.md` Principle 1, `ELEVATION.md`, `TYPOGRAPHY.md`). One consistent visual language — one icon set, one type scale, one spacing scale, one shadow scale — applied everywhere, because a large product surface only feels coherent if its smallest visual decisions are made once, centrally, and reused (`COLORS.md`, `SPACING.md`, `ICONS.md`).

### 3. UX Philosophy

Every screen has exactly one primary action. Every list, table, and panel has a genuine, considered empty state, loading state, and error state — not an afterthought (`DESIGN_PRINCIPLES.md` Principles 3 and 5, `SCREEN_PATTERNS.md` patterns 30–32). Reversible actions are undoable; irreversible actions are confirmed, specifically, never generically (`UX_PATTERNS.md` → Undo, Confirmation).

### 4. Interaction Philosophy

Motion explains state changes; it never performs for its own sake. Nothing animates for longer than roughly 320ms. Every interactive element has a visible focus state, a real hover/active state, and a keyboard path — mouse-only and animation-only interactions are both defects (`MOTION.md`, `ACCESSIBILITY.md`).

### 5. Navigation Philosophy

CareHub navigation adapts to role and business type — a user never has to visually filter past modules that aren't theirs. CareFind navigation stays shallow (search → results → detail) and always visible (persistent bottom tab bar / header nav) — a first-time, possibly anxious user should never wonder "how do I get back" (`NAVIGATION.md`).

### 6. Information Architecture Philosophy

Every screen answers, in this order: what am I looking at (identity) → what matters most right now (hierarchy) → what can I do about it (action) → what else is here (secondary content). This ordering is never inverted (`SCREEN_PATTERNS.md`, `LAYOUTS.md`).

### 7. Accessibility Philosophy

WCAG 2.1 AA is the floor for every screen, not an aspirational target reserved for a later pass. Color is never the sole carrier of meaning. Everything reachable by mouse is reachable by keyboard. Every state change that matters is announced to assistive technology (`ACCESSIBILITY.md`).

### 8. Responsive Philosophy

Every breakpoint is a deliberate design decision, not a scaled-down copy of the one above it. CareHub is designed desktop-first and extends down; CareFind is designed mobile-first and expands up. Tables become card lists on mobile; filters become bottom sheets; sidebars become drawers or tab bars — because these are the intentionally correct shapes for small screens, not compromises (`RESPONSIVENESS.md`, `COMPONENT_LIBRARY.md`).

## Part 2: The Review Checklist

Run this against **every** new screen, component, or workflow before it ships — whether designed by a human or generated by an AI assistant reading these documents. A screen that fails any item under "Non-negotiable" should not ship until fixed. Items under "Judgment call" require a documented reason if skipped, not a silent pass.

### Design system compliance
- [ ] Colors are drawn from `COLORS.md`'s palette only — no ad hoc hex values.
- [ ] Type sizes/weights match `TYPOGRAPHY.md`'s scale — no arbitrary font sizes.
- [ ] Spacing uses `SPACING.md`'s 4px-based scale — no arbitrary margin/padding values.
- [ ] Icons come from the single system icon set (`ICONS.md`) — emoji only where explicitly permitted (user-generated content).
- [ ] Shadows/elevation match `ELEVATION.md`'s 5-level scale — no custom box-shadows.
- [ ] Corner radius is consistent with existing component conventions, not decided per-screen.

### Screen pattern compliance
- [ ] The screen matches an existing pattern in `SCREEN_PATTERNS.md`, or a deliberate, documented extension of one — not an unrelated one-off layout.
- [ ] The screen uses one of the templates in `LAYOUTS.md` — not a bespoke structural layout.
- [ ] If this is genuinely a new pattern with no match, that decision is explicit and `SCREEN_PATTERNS.md` is updated, not silently worked around.

### Accessibility (non-negotiable)
- [ ] Every interactive element is keyboard-reachable and has a visible focus state.
- [ ] Every image/icon conveying meaning has real accessible text.
- [ ] Color is never the only signal (status, error, selected state all have a second cue).
- [ ] Form fields have real, associated labels — not placeholder-as-label.
- [ ] Touch targets are ≥44×44px (mobile) / ≥32×32px (desktop, `ICONS.md`).
- [ ] Contrast meets WCAG AA for all text and meaningful icons (`ACCESSIBILITY.md`).

### Responsiveness (non-negotiable)
- [ ] The screen has been designed — not merely scaled — for Mobile, Tablet, and Desktop.
- [ ] Tables (if any) transform to a card list on mobile, per `COMPONENT_LIBRARY.md` — not horizontal scroll as the primary strategy.
- [ ] Forms are single-column on mobile.
- [ ] Filters use a bottom sheet on mobile, not a squeezed inline row or hidden sidebar.
- [ ] Navigation collapses per `NAVIGATION.md`'s defined pattern for this breakpoint (rail/drawer for CareHub, tab bar/header for CareFind) — not left broken or improvised.

### Information hierarchy
- [ ] There is exactly one primary action, visually distinct from every secondary action.
- [ ] The most important information is legible without scrolling, at the target breakpoint.
- [ ] Hierarchy is established via type/spacing/color before any decorative element is introduced.

### UX quality
- [ ] Loading, empty, and error states are all designed — not one generic placeholder covering all three.
- [ ] Irreversible actions require specific confirmation; reversible actions offer undo instead of a confirmation dialog.
- [ ] Validation errors are specific, adjacent to their field, and never clear the user's input.
- [ ] If the screen involves saving, it's clear to the user whether that save is automatic or explicit.

### Visual consistency
- [ ] The screen looks and feels like it belongs to the same product as every other screen around it — not a visually distinct "special case."
- [ ] Component usage matches `COMPONENT_LIBRARY.md` — no redesigned one-off buttons, inputs, or cards.

### Professional appearance
- [ ] No gradient used purely decoratively (`ELEVATION.md`, `BRAND_GUIDELINES.md` — gradients are reserved for their one defined use, primary buttons/brand marks).
- [ ] No card-on-card nesting (`ELEVATION.md`'s named "AI-generated tell").
- [ ] No more than one accent color competing for attention on a single screen.
- [ ] Copy tone matches `BRAND_GUIDELINES.md`'s voice — calm, direct, professional; never cute, alarmist, or filler.

### Enterprise readiness (CareHub especially)
- [ ] The screen holds up at real data density (dozens/hundreds of rows), not just the two or three sample rows used while designing it.
- [ ] Role-based visibility is respected — a user only sees actions/nav items their role permits, never a shown-then-disabled control (`SCREEN_PATTERNS.md` → Patient Profile).
- [ ] Keyboard efficiency is possible for power-user workflows (`NAVIGATION.md`).

### Healthcare appropriateness
- [ ] Nothing about the screen's tone or visuals trivializes a clinical or financial action — no celebratory confetti/animation on a medical or billing outcome.
- [ ] Sensitive information (patient data, financial figures) is never exposed in a state where it shouldn't be (e.g., a Permission Denied screen never previews restricted content, `SCREEN_PATTERNS.md` pattern 33).
- [ ] Status/urgency signals (lab priority, patient pipeline state) use the system's semantic color scale consistently — clinical urgency is never miscommunicated by an inconsistent color choice.

## How to use this document

1. Before designing: find the closest match in `SCREEN_PATTERNS.md` and `LAYOUTS.md`. Don't start from a blank page.
2. While designing: build from tokens and components already defined in `DESIGN_SYSTEM.md` — don't invent new values.
3. Before shipping: run this checklist. Non-negotiable items block shipping. Judgment-call items need a stated reason if skipped.
4. If nothing in the existing system fits: that's a signal to extend the system deliberately (propose an addition to the relevant document) — not to freelance a one-off that quietly drifts the product away from its own standards.

This is the mandatory reference for every future feature. No new page, component, or workflow should be designed without first following these standards and selecting the closest matching screen pattern from `SCREEN_PATTERNS.md`.
