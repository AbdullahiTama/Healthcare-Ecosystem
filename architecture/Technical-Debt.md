## Methodology

**Effort** (cost to remediate, one engineer familiar with the codebase):
`XS` <1 day · `S` 1–2 days · `M` 3–5 days · `L` 1–2 weeks · `XL` 3+ weeks / requires architectural change

**Risk** (consequence of leaving it as-is):
`Severe` — data breach, clinical harm, financial loss, or core function silently broken · `High` — significant user-facing failure or security exposure under realistic conditions · `Moderate` — degraded UX or maintainability drag · `Low` — cosmetic/hygiene

### Native browser prompt → toast/ConfirmDialog sweep, 2026-07-19

Requested via `/frontend-design`: audit and fix loading-state UI and toast coverage in both apps, and replace `alert()`/`confirm()`/`prompt()` with in-app equivalents. Audit found both apps already had a `Toast`/`useToast`/`Loading` foundation (CareFind's built explicitly to mirror CareHub's, plus `Skeleton`/`CardSkeleton`/`ConfirmDialog` — the latter already governed by a full design-system doc set at `docs/design/` that neither app was fully following yet) — the gap was adoption, not absence: 187 native `alert()`/`confirm()`/`prompt()` calls across 35 files (105 CareHub, 82 CareFind).

Per `docs/design/DESIGN_PRINCIPLES.md` principle 9 and `SCREEN_PATTERNS.md`'s Confirmation Dialog pattern, `confirm()` calls were **not** blanket-converted to toast (a toast can't gate a blocking yes/no decision) — each was classified per-site as hard-to-reverse (→ `ConfirmDialog`, CareHub's newly built to match CareFind's, with a specific stated consequence, never a generic "Are you sure?") or routine/reversible (→ action performed directly, toast shown, with an Undo action only where a real restore path existed in the code). The one `window.prompt()` (CareFind's `PlaylistView.jsx`, editing a part title) became a true inline edit instead, since neither toast nor a confirm dialog can capture text input.

Result: 163 `alert()` → typed toasts (success/error/warning/info, chosen from message content; vague error copy sharpened per `UX_PATTERNS.md`'s Error Recovery rule), 23 `confirm()`/`window.confirm()` → `ConfirmDialog` or direct-action-plus-toast per the classification above, 1 `window.prompt()` → inline edit. Zero native browser prompts remain in either app's `src/` (verified by grep post-sweep). Both apps' `vite build` clean throughout and after.

Sequenced by dependency and leverage, not strictly by tier.

**Phase 0 — Verify (days):** C8 (schema check), H4 (webhook reachability), C7 (crash repro), M10 (Anthropic call). Pure verification; each result changes how urgently its paired fix matters.

**Phase 4 — Everything else:** Remaining Medium items in listed order; Low-tier hygiene opportunistically; pull L5 (test suite) earlier than "last" if capacity allows — starting it alongside Phase 1–2 changes de-risks every phase after it.
