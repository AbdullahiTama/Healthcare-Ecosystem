# Missing Documentation — Care Ecosystem

What a new engineer cannot currently learn from this repository, and has to instead reverse-engineer from source code (as every document in this `architecture/` folder was forced to do).

## Gaps that block safe, confident work

1. **No database schema, migration, or ERD anywhere in either product**, despite CareHub and CareFind apparently sharing one physical Supabase project across ~76 tables. Every table, column, and relationship documented in `Database.md` was reconstructed by reading query strings — there is no way to confirm foreign keys, constraints, or RLS policies from the repository itself. This is the single most consequential documentation gap in the ecosystem, and the direct cause of `Database.md`'s unresolved `consultations` naming-collision risk.
2. **No auth/security model documentation.** Given `Security-Risks.md`, this is the most urgent gap after the schema — a written model (even a short one) stating which of the four authentication systems is authoritative, what each is supposed to guarantee, and what "logged in" means across product boundaries would have caught at least the `admin-auth.js`/`admin-setup.js` hash mismatch before it shipped.
3. **No documentation of the CareHub ↔ CareFind data relationship.** `visible_on_carefind`/`list_on_carefind`, `staff_claims`, and `business_claims` are real, working integration points with no written contract anywhere describing what either side promises the other. `Shared-Services.md` is this engagement's attempt to write that contract retroactively; it should be treated as a first draft to be corrected against the live schema and each team's actual intent, not a finished spec.
4. **`knowledge/modules/` is completely empty** — no per-module documentation exists for any of CareHub's ~20 dashboard modules or CareFind's ~48 screens, despite `templates/MODULE_DOCUMENTATION_TEMPLATE.md` existing specifically for this purpose. The five CareHub module deep-dives produced earlier in this engagement (Inventory, Patients, Hospital, Pharmacy, Laboratory) are a starting point but cover only a fraction of either product's surface.
5. **`planning/CODE_AUDIT.md` is a template with every section empty.** The audit `planning/roadmap.md`'s own Phase 1 calls for has never been performed until this engagement.
6. **`architecture/` and `decisions/` were empty at the start of this engagement.** No ADRs exist anywhere, despite this project's own engineering brief instructing that architectural changes be proposed and documented before implementation. This document set populates `architecture/`; `decisions/` remains empty and worth starting deliberately — even a handful of ADRs covering "why does CareHub hand-roll PostgREST calls instead of using supabase-js" or "why do CareHub and CareFind use different auth systems" would resolve real ambiguity for the next engineer who wonders whether those were deliberate choices or accidents of history.
7. **No README exists for CareFind** (CareHub has one, not reviewed in depth this engagement — worth a follow-up pass to confirm it's current). CareFind has no equivalent at all, which is a real gap given it's the larger of the two codebases by line count.
8. **No environment/configuration documentation in either product.** No `.env.example`, no documented list of required environment variables (Supabase URL/key, `ADMIN_SECRET_SALT`, `PAYSTACK_SECRET_KEY`, whatever the Anthropic API key situation in `lib/reviewAI.js` actually is) — a new engineer cannot know what to configure without reading every source file that references `process.env.*`.
9. **No documentation of CareFind's actual scope.** `docs/PROJECT_OVERVIEW.md` describes a healthcare discovery platform; the implementation is overwhelmingly a social/live-streaming/creator platform (`CareFind-Architecture.md`). Whether this divergence is intentional product evolution the docs simply haven't caught up to, or scope creep nobody has stepped back to evaluate, cannot be determined from the repository — but the gap itself should be named explicitly rather than left for each new engineer to independently discover, as this engagement had to.
10. **No test documentation, because no tests exist.** Neither `package.json` lists a test runner; no `__tests__`/`*.test.*`/`*.spec.*` files were found in either product. This isn't strictly a documentation gap, but the absence of any stated testing strategy (even "we don't test yet, here's why and here's the plan") means a new engineer has no way to know whether this is an intentional stage-of-company tradeoff or an oversight.

## What exists and is worth keeping

`knowledge/business/PRODUCT_PRINCIPLES.md` and `PROJECT_VISION.md`, `knowledge/glossary/TERMS.md`, and `knowledge/workflows/MASTER_WORKFLOW.md` are genuinely useful, well-written domain documentation — the healthcare-domain thinking in these files (FEFO, the patient-journey workflow) is real and not generic scaffolding. They just have no bridge to the code that's supposed to implement them, which is what this `architecture/` folder now provides on the CareHub side and partially on the CareFind side.

## Recommended next documentation investment, in order

1. A written database schema doc (even a hand-maintained one, pending real migrations) — resolves the highest number of downstream unknowns per hour invested.
2. A one-page auth/security model — short, but the highest-leverage single page given `Security-Risks.md`.
3. `Shared-Services.md`'s content, formalized and agreed by whoever owns each product, turned from this engagement's reverse-engineered draft into an actual maintained contract.
4. Module docs for CareFind's admin/creator-monetization surface, given it's the largest and least-documented part of the entire ecosystem.
