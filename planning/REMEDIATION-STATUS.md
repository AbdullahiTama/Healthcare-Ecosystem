### C15 — Wallet/payment hardening, applied to production 2026-07-18

Found during a review requested specifically for CareFind's payment surface (`initiate-payment.js`, `verify-payment.js`, `paystack-webhook.js`, `api/_lib/paystackCredit.js`, `Wallet.jsx`'s top-up/withdrawal flow, `admin-auth.js`'s withdrawal actions — the last three of these were already-uncommitted work in the working tree when the review started).

**Critical, live: two vulnerable `send_gift` overloads.** The database had 4 versions of `send_gift` stacked up from earlier iterations — 2 safe (`auth.uid()`-derived sender, from C14), and 2 that took `p_sender` as a caller-supplied argument while still being `SECURITY DEFINER`. Any authenticated user could call `POST /rest/v1/rpc/send_gift` directly with someone else's uuid as `p_sender` and drain their wallet, entirely bypassing the app — confirmed via grep that `GiftPanel.jsx`/`LiveSession.jsx` never call the vulnerable shape, so this was pure leftover cruft, not something the app relied on. Fixed by dropping both overloads.

**Severe: the new top-up flow's crediting wasn't actually atomic.** `verify-payment.js` (fires on redirect back from Paystack) and `paystack-webhook.js` (Paystack's own async notification, the backup path for a missed redirect) are *designed* to race the same reference — the code's own comments said so. But `creditTopup()` did a JS-level check-then-act (check `transactions.reference` exists, read wallet balance, write) with no DB-level uniqueness on `reference` — a genuine concurrent double-fire could lose an update or duplicate a transaction row. `admin-auth.js`'s `reject_withdrawal` had the identical pattern for its refund. Fixed by adding a partial unique index (`transactions.reference` where `type='topup'`) and three new `SECURITY DEFINER` RPCs — `credit_wallet_topup`, `approve_withdrawal_request`, `reject_withdrawal_request` — each doing its read-check-write as one atomic, row-locked unit, mirroring the existing `pay_creator_subscription`/`send_gift`/`request_withdrawal` pattern. Unlike those, all three are explicitly `REVOKE`d from `anon`/`authenticated` (verified via `pg_proc.proacl` post-migration), since they trust their arguments directly rather than deriving identity from `auth.uid()` — they're only ever called by already-server-verified code.

**Also fixed, same session: `paystack-webhook.js`'s signature check.** It hashed `JSON.stringify(req.body)`, but Vercel's default body parser had already parsed the body into a JS object — re-serialized JSON isn't guaranteed byte-identical to what Paystack actually signed, which could make genuine webhooks fail verification. Fixed by disabling the parser (`export const config = { api: { bodyParser: false } }`) and hashing the true raw bytes. This also closes H4 (the file's move from the project root into `api/` — already done in the working tree before this review started — is now confirmed correct against `vercel.json`'s rewrite rule).

All four fixes shipped as one migration, `apps/carefind/sql/wallet_payment_hardening.sql`, applied directly to production on your explicit go-ahead (via `AskUserQuestion`, same pattern as every other production-impacting step this engagement). Verified post-migration: `pg_proc` shows only the 2 safe `send_gift` overloads remain; the 3 new functions' ACLs show `postgres`/`service_role` only, no `anon`/`authenticated`. `get_advisors` (security) shows no new findings on any of the new objects. Clean `vite build` of CareFind; `node --check` on all 5 touched/reviewed Vercel functions. Full detail in `Technical-Debt.md` under C15 (new), C11 (now resolved), H4 (now resolved).
