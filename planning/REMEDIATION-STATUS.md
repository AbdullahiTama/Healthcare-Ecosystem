### Phase 2 — RLS for CareHub — **APPLIED TO PRODUCTION, 2026-07-18**
`apps/carehub/sql/phase2_rls_pilot.sql` — all 40 CareHub tables, three policy shapes (direct `business_id`, join-through-parent for FK-only child tables, `auth.uid()` for the two CareFind bridge tables). **You explicitly authorized running this against production**, with the known, accepted consequence that the 7 not-yet-migrated accounts (see item 2 below) would lose access to their own data until they next log in.

**What happened when it ran:** first attempt failed outright — `is_platform_admin()` referenced `businesses.is_platform_admin`, a column that turned out not to exist in the live database at all (see the Phase 0 correction above). The migration is transactional; verified the failure rolled back completely (zero policies/functions created) before touching anything else. Added the missing column (`ALTER TABLE businesses ADD COLUMN is_platform_admin boolean DEFAULT false`, additive/safe), then re-ran the full file successfully. **Verified after applying**: 0 remaining `qual:true` policies across all 40 tables, both helper functions (`current_business_ids`, `is_platform_admin`) exist, all 40 tables have real policies.

**Current live consequence, accepted knowingly**: the 7 unmigrated CareHub accounts (6 businesses, 1 staff) have no access to their own data right now, until they log in again (which silently completes their migration to a real session). **You still need to set `is_platform_admin = true` on your own business row** — the column exists but nobody has it set, so platform-admin login doesn't work yet either.

**H11 — Fixed.** CareFind's `AdminPanel.jsx` `approveClaim()`/`rejectClaim()` wrote `business_claims` and `businesses.visible_on_carefind` directly from the browser with the plain anon key, no Supabase Auth session. Now routed through two new actions (`approve_claim`/`reject_claim`) on `api/admin-auth.js`, same service-role pattern already used for `admin_users`/`admin_teams` (C9). Verified with a clean `vite build` of the CareFind app. Scope correction from the original finding: `AdminPanel.jsx` never actually touched `staff_claims` — only `business_claims`/`businesses`. `staff_claims` approval is entirely CareHub-side (`Staff.jsx`) and turned out to have its own, separate version of this problem — see C10.

**C10 — Fixed, and the grants question is now resolved too.** Found while verifying H11's fix was complete: CareHub's `lib/supabase.js`/`sbFetch()` — the function behind every one of `phase2_rls_pilot.sql`'s 40 tables, including `approveStaffClaim`/`rejectStaffClaim` — hardcoded the anon key as its `Authorization` header on every request, unconditionally, never reading from `lib/authClient.js`'s real Phase 1 login session. Fix: `sbFetch()` plus the three storage-upload functions (which had the identical bug, independently, each hardcoding the anon key inline — consolidated into one shared `sbUpload()` helper while fixing it, removing a triplication) now call a shared `authToken()` that reads `authClient.auth.getSession()` and forwards the real token when one exists, anon key otherwise. Because all ~90 CareHub data functions already funneled through this one shared function, the fix needed no per-call-site changes and no separate audit of pre-login flows — they fall back to the exact same anon-key behavior they always had. Verified with a clean `vite build`. **Live-verification item, now checked:** this switches logged-in users from Postgres role `anon` to `authenticated`; queried `information_schema.role_table_grants` directly against the live project and confirmed `authenticated` carries identical grants to `anon` on every `public`-schema table (see "Blocked on you" #1). Deploying this fix will not cause new failures on that front. Full writeup in `architecture/Technical-Debt.md` under C10 and the corrected C1; the SQL file's header comment carries the same note inline.

**H10 — Fixed.** CareFind's `AdminPanel.jsx` `loadAll()` destructures a 12-item `Promise.all`; positions 8–12 of the query array had drifted out of sync with their destructured variable names (confirmed, not just suspected, by tracing every downstream use): the Staff tab was rendering `businesses` rows, the Withdrawals tab was rendering `staff` rows, the Task Submissions tab was rendering `withdrawal_requests` rows, the "new consultation booking" notification was built from `task_submissions` data, and the Businesses tab was rendering `consultations` rows. Every consumer of the five affected variables (`setStaff`, `setWithdrawals`, `setBusinesses`, the notification-feed builder, the pending-count stats) already referenced them by their intended name, so the fix was a single-line reorder of the destructuring assignment to match query order — no query or render code changed, no ambiguity once traced, so the "needs a human to confirm intended behavior per tab" flag from a prior session was resolved by tracing rather than by discovering the tabs actually wanted something different. User confirmed proceeding before the change. Verified with a clean `vite build`.

**C14 — Both halves now addressed.** Discovered incidentally while building CareFind's schema reference: every table in the live database has Postgres RLS "enabled" (`relrowsecurity = true`) but neutralized by a pre-existing PERMISSIVE policy — Postgres ORs permissive policies together, so this makes RLS's "enabled" flag actively misleading: a dashboard checkmark or security scanner would report these tables as protected when they're not. CareHub half fixed as described above. **CareFind half — this session, in three parts:**

1. **Code fix, following the H11/C9 pattern**: every "Admin"-named `qual:true` policy this item flagged (`verification_requests`, `withdrawal_requests`, `reports`, `transactions`, `task_submissions`, `business_claims`, `profiles`) can only be safely dropped once nothing in the app still depends on that fake-permissive access — so before touching any SQL, every `AdminPanel.jsx` read and write touching those tables (plus `posts`, `news`, `stories`, `live_shows`, `live_items`, `live_comments`, `promotions`, and a full 7-table cascading `deleteUser()`) was moved behind `api/admin-auth.js`'s service-role client: **24 new write actions** (`approve_verification`, `reject_verification`, `manual_verify`, `suspend_user`, `delete_user`, `delete_post`, `resolve_report`, `create_task`, `approve_withdrawal`, `reject_withdrawal`, `schedule_show`, `start_live_show`, `start_scheduled_show`, `cancel_scheduled_show`, `end_live_show`, `post_live_item`, `hide_live_comment`, `create_promotion`, `delete_promotion`, `approve_news`, `reject_news`, `delete_news`, `create_story`, `delete_story`) and **7 new list-read actions** (`list_verification_requests`, `list_reports`, `list_transactions`, `list_withdrawal_requests`, `list_task_submissions`, `list_business_claims`, `list_news`, `list_search_logs`). Verified with clean `vite build`s and a Node syntax check of `admin-auth.js` (a Vercel serverless function, not bundled by Vite).
2. **A more serious version of C11, found and fixed along the way**: `GiftPanel.jsx`/`LiveSession.jsx` performed raw client-side writes crediting *other users'* `wallets`/`transactions` rows directly from the sender's browser session — not just non-atomic (C11's framing), no ownership check whatsoever, meaning any authenticated user could write an arbitrary balance to any other user's wallet. Fixed with a new `send_gift` SECURITY DEFINER RPC mirroring the existing `pay_creator_subscription` pattern (row-locks the sender's wallet, computes the split server-side, atomic) — **already applied to the live database** and wired into both client files. This was self-contained (no RLS dependency) so it shipped ahead of the SQL draft.
3. **SQL draft**: `apps/carefind/sql/carefind_rls_hardening.sql` (new, "DO NOT RUN AGAINST PRODUCTION YET" — same draft-only status as CareHub's file). Unlike CareHub's tables (one blanket policy each), most CareFind tables already had a correctly-scoped policy sitting *alongside* the dangerous one — so this is a surgical DROP-the-bad-one pass, not a rewrite, verified table-by-table against both the live policy definitions and every non-admin call site (researched exhaustively, not sampled). Also fixed along the way: a real ownership-check gap on `products`/`playlists`/`playlist_parts`/`live_shows`/`live_participants`/`live_comments`/`creator_subscriptions`/`user_reviews`/`notifications` (each had a blanket "manage X" policy with zero per-user check, exploitable directly via the REST API regardless of what the UI does), and three tables/columns with RLS enabled and **zero policies at all** (`subscriptions`, `user_subscriptions`, `wallets`' missing INSERT, `task_submissions`' missing INSERT, `live_messages`' missing DELETE) — meaning those features have been silently broken in production this whole time, independent of anything here; the fix restores them as a side effect, not a security change.

Full detail in `Technical-Debt.md` under C14.
