- [x] **C20a — RESOLVED 2026-08-08. Both public forms — business registration and referral-agent application — failed for every user, and the recorded root cause was wrong.** Symptom: `Register.jsx` showed "Registration failed: … new row violates row-level security policy for table "businesses"". `20260805_public_form_insert_policies.sql` diagnosed a missing anon INSERT policy and shipped one; the forms stayed broken, because that was never the cause. **Re-measured against production with the exact request the app sends:** `POST /rest/v1/businesses` with `Prefer: return=minimal` → **201**, with `Prefer: return=representation` → **42501**. Identical result on `agent_applications`. The INSERT policy exists and passes. `return=representation` — which `sbFetch` sends by default — makes PostgREST emit `INSERT … RETURNING`, and **PostgreSQL applies the SELECT policy to the new row whenever an INSERT carries a RETURNING clause**. Neither table lets an anonymous caller read what it just wrote: `businesses`' only anon SELECT policy is the public directory (`status='active'`, while every new signup is `status='pending'`), and `agent_applications` is a write-only intake queue with no anon SELECT policy at all. The insert succeeded, the RETURNING check failed, the transaction rolled back, and the client got a 42501 naming the INSERT policy — which is what sent the previous pass looking in the wrong place.
  Fixed in the client, no database change needed: `registerBusiness()` and `submitAgentApplication()` send `Prefer: return=minimal`. Both discard the response, and an anonymous caller must not be able to read back a row holding a password (see C20). Regression test at `apps/carehub/src/services/__tests__/anonymousInserts.test.js`; the superseded file's header now carries the correction. Clean `vite build`, 258/258 tests pass.
  **Lesson: reproduce with the request the application actually sends, headers included.** The earlier probe differed from the app by one header and proved the opposite of the truth. The file's own verification step told the next reader to probe the same misleading way.

The residual "confirm email effectively ON" Medium item is moot for the CareHub registration/staff-provisioning paths (both mint confirmed users server-side), but remains a live caveat for any account that reaches Supabase's generic `signUp` directly.
- [x] **C19 — RESOLVED IN PRODUCTION 2026-08-05. C14 was never actually fixed on 16 CareHub tables: every row readable AND writable by anyone holding the public anon key, not logged in.** Found while checking RLS on `staff` before writing the staff repository. Postgres ORs PERMISSIVE policies, so one `qual: true` policy defeats every scoped policy on the table — 60 such policies existed across 55 tables, 25 of them `cmd = ALL`. **Proven as an unauthenticated caller** (read-only probe, rolled back): 12 staff rows across 5 businesses *all with plaintext passwords set* (C2's legacy columns), 5 clients, 54 sales, 9 debts, 3645 products, 1 role.
  **This was NOT drift, and correcting the record matters: `phase2_rls_pilot.sql`'s DROP statements named policies that do not exist.** The file says `DROP POLICY IF EXISTS "Allow all staff" ON staff` (likewise products/sales/clients/debts/purchases); the live policies are all named plain `"Allow all"`. `DROP POLICY IF EXISTS` on a wrong name is a **silent no-op** — no error, nothing to notice. The file's own line 117 gets it right for `businesses` (unsuffixed), which is why that one table really is clean and made the whole file look like it had worked. No migration after `phase2_rls_pilot_carehub` touches these tables.
  Fixed by dropping **by predicate, not by name** (`qual = 'true'` on an explicit 16-table list), since naming is precisely what failed before, with a guard that aborts if any listed table would be left with zero policies. Verified three ways: the anon probe re-run (12/5/54/9/3645/1 → all 0), the catalog (0 blanket left, every table still has a scoped policy), and — the risk that matters most here — **every non-platform-admin owner with staff impersonated to confirm nobody was locked out** (each saw exactly their own rows, zero foreign rows, `current_business_ids()` = 1). Advisors unchanged. SQL and full evidence in `apps/carehub/sql/20260805_c14_regression_drop_blanket_policies.sql`.

Plus ~32 SELECT-only `qual: true` policies that are mostly CareFind's intentional public feed, and the `admin_users`/`admin_teams`/`admin_notifications` policies already flagged for their own pass.

- [ ] **Original C5 evidence (retained, 2026-08-04).** This is **not a new finding**: C5 has been tracked as Severe since the original audit, and `C12` is its mirror image (`Purchases.jsx` never replenishes stock on receipt, so neither side of the inventory lifecycle maintains `products.stock`). What is new is only the server-side half of the proof — C5 was established by reading application code, and nobody had ruled out the database doing the work. It doesn't. See C5/C12 in `architecture/Technical-Debt.md` for the canonical entries; the detail below is the evidence, not a separate item.
  `POS.jsx` reduces stock only via `setProducts(...)` (`charge()` and `chargeCredit()`), which is React state owned by `BusinessDashboard.jsx` and re-seeded from the database by `loadProducts()` on every mount. So the decrease a cashier sees is cosmetic and is overwritten on the next page load. No client-side write touches `products.stock` on a sale: POS never calls `updateProduct`, and `stock_batches` (Stock.jsx transfer/adjust) is a separate mechanism not wired to sales. Corroborating: the inventory seam commit removed an `updateStock` that was dead and malformed — client-side stock persistence was clearly intended here and never worked.
  **Verified server-side, not assumed:** a `pg_trigger`/`pg_proc` query against the live `carehub` project returned **zero rows** — no trigger on `sales`/`products`/`stock_batches`/`stock_movements`, and no `public` function whose body even mentions stock. Nothing decrements `products.stock` anywhere.
  Consequences: `products.stock` is overstated by every unit ever sold; POS out-of-stock and low-stock badges, Inventory's stock/cost valuation totals, and the CareFind listing filter (`stock > 0`) are all computed from a number that only ever goes up. **Historical stock values cannot be reconstructed from `products` alone** — a fix going forward does not repair existing quantities, and any backfill would have to be derived from the `sales.items` JSON. Fix design is an open decision (trigger on `sales` vs. an RPC called by the sale repository); it also needs rules for held sales, Services-category lines, and whether stock may go negative.

- [x] **The 1000-row clamp was never actually fixed — offset paging now is (2026-08-11).** Commit `3fbed5a` "removed the 1000-product silent cap" by raising the client-side `limit` to 50000. That does nothing: PostgREST's server-side `db-max-rows` (default 1000) clamps every response regardless of the requested limit. **Proven against the live project:** `GET products?select=id&limit=50000` with `Prefer: count=exact` returned `Content-Range: 0-999/12276` — 12,276 rows in the table, 1000 returned. Wired into every tenant collection read: `productRepository.getAll`, `clientRepository.getAll`, `masterCatalogRepository.getAll`, `getLinks`, and the legacy `getProducts`/`getClients` in `services/supabase.js`.
