- [x] **C20a — RESOLVED 2026-08-08. Both public forms — business registration and referral-agent application — failed for every user, and the recorded root cause was wrong.** Symptom: `Register.jsx` showed "Registration failed: … new row violates row-level security policy for table "businesses"". `20260805_public_form_insert_policies.sql` diagnosed a missing anon INSERT policy and shipped one; the forms stayed broken, because that was never the cause. **Re-measured against production with the exact request the app sends:** `POST /rest/v1/businesses` with `Prefer: return=minimal` → **201**, with `Prefer: return=representation` → **42501**. Identical result on `agent_applications`. The INSERT policy exists and passes. `return=representation` — which `sbFetch` sends by default — makes PostgREST emit `INSERT … RETURNING`, and **PostgreSQL applies the SELECT policy to the new row whenever an INSERT carries a RETURNING clause**. Neither table lets an anonymous caller read what it just wrote: `businesses`' only anon SELECT policy is the public directory (`status='active'`, while every new signup is `status='pending'`), and `agent_applications` is a write-only intake queue with no anon SELECT policy at all. The insert succeeded, the RETURNING check failed, the transaction rolled back, and the client got a 42501 naming the INSERT policy — which is what sent the previous pass looking in the wrong place.
  Fixed in the client, no database change needed: `registerBusiness()` and `submitAgentApplication()` send `Prefer: return=minimal`. Both discard the response, and an anonymous caller must not be able to read back a row holding a password (see C20). Regression test at `apps/carehub/src/services/__tests__/anonymousInserts.test.js`; the superseded file's header now carries the correction. Clean `vite build`, 258/258 tests pass.
  **Lesson: reproduce with the request the application actually sends, headers included.** The earlier probe differed from the app by one header and proved the opposite of the truth. The file's own verification step told the next reader to probe the same misleading way.

The residual "confirm email effectively ON" Medium item is moot for the CareHub registration/staff-provisioning paths (both mint confirmed users server-side), but remains a live caveat for any account that reaches Supabase's generic `signUp` directly.
- [x] **C19 — RESOLVED IN PRODUCTION 2026-08-05. C14 was never actually fixed on 16 CareHub tables: every row readable AND writable by anyone holding the public anon key, not logged in.** Found while checking RLS on `staff` before writing the staff repository. Postgres ORs PERMISSIVE policies, so one `qual: true` policy defeats every scoped policy on the table — 60 such policies existed across 55 tables, 25 of them `cmd = ALL`. **Proven as an unauthenticated caller** (read-only probe, rolled back): 12 staff rows across 5 businesses *all with plaintext passwords set* (C2's legacy columns), 5 clients, 54 sales, 9 debts, 3645 products, 1 role.
  **This was NOT drift, and correcting the record matters: `phase2_rls_pilot.sql`'s DROP statements named policies that do not exist.** The file says `DROP POLICY IF EXISTS "Allow all staff" ON staff` (likewise products/sales/clients/debts/purchases); the live policies are all named plain `"Allow all"`. `DROP POLICY IF EXISTS` on a wrong name is a **silent no-op** — no error, nothing to notice. The file's own line 117 gets it right for `businesses` (unsuffixed), which is why that one table really is clean and made the whole file look like it had worked. No migration after `phase2_rls_pilot_carehub` touches these tables.
  Fixed by dropping **by predicate, not by name** (`qual = 'true'` on an explicit 16-table list), since naming is precisely what failed before, with a guard that aborts if any listed table would be left with zero policies. Verified three ways: the anon probe re-run (12/5/54/9/3645/1 → all 0), the catalog (0 blanket left, every table still has a scoped policy), and — the risk that matters most here — **every non-platform-admin owner with staff impersonated to confirm nobody was locked out** (each saw exactly their own rows, zero foreign rows, `current_business_ids()` = 1). Advisors unchanged. SQL and full evidence in `apps/carehub/sql/20260805_c14_regression_drop_blanket_policies.sql`.
  **Still open, deliberately out of scope:** 9 tables with a blanket `ALL` policy and **no** scoped policy at all (`admin_team`, `follow_ups`, `patient_requests`, `requisition_items`, `rep_colleagues`, `rep_company_entries`, `rep_customer_entries`, `rep_customers`, `rep_peer_entries`) — dropping alone would deny everything, so they need policies written first. Plus ~32 SELECT-only `qual: true` policies that are mostly CareFind's intentional public feed, and the `admin_users`/`admin_teams`/`admin_notifications` policies already flagged for their own pass.
  **Lesson, and it is the second instance of the same shape today:** a DDL statement completing is not evidence it did anything — see also the `REVOKE ... FROM PUBLIC` trap in `20260805_atomic_stock_transfer.sql`. Re-read the catalog. `IF EXISTS` converts a typo into silence.

- [x] **admin_users / admin_teams / admin_notifications — RESOLVED IN PRODUCTION 2026-08-15 (P0 #3 in roadmap.md §6). The last known C19-shape hole in CareFind: three admin tables with RLS "enabled" but neutralized by `qual:true` policies.** `admin_users` had a SELECT policy (`"Allow admin login check"`, `qual:true` — anyone, including unauthenticated requests carrying the anon key, could read every admin row: email, `password_hash`, role, team_id) and an UPDATE policy (`"Allow admin users to update their own record"`, `USING(true)` — despite the name, ANY authenticated user could update ANY admin row: privilege escalation to `super_admin` or a password reset). `admin_teams` had a public-read SELECT (`"Allow reading teams"`). `admin_notifications` had public-read SELECT + UPDATE + an unguarded INSERT `with check` (zero rows, zero code references). Dropping the policies therefore cannot break login, list, create, toggle or setup.

Result: RLS stays enabled with ZERO policies on all three tables — deny-all for anon/authenticated, service-role-only access, the same posture `withdrawal_requests` already has.
  **Verified behaviorally, not from the catalog:** `pg_policies` returns no rows for all three tables; `relrowsecurity` still true; `anon` SELECT returns 0 rows; `authenticated` UPDATE affects 0 rows and is rejected; both roles confirmed `rolbypassrls=false` and not table owners (so RLS genuinely applies); service-role (the admin API's client) still reads `admin_users` fine — both admin rows intact, `is_active` true. - [x] **C18 — RESOLVED IN PRODUCTION 2026-08-05. Privilege escalation: any business owner could make themselves a platform admin with one PATCH.** Found while checking whether the tracked `saveBizDetails` whitelist item was worth doing — it was, but not for the stated reason: the whitelist is client-side, and the server had no column protection at all. `businesses`' only general policy is `ALL` with `qual`/`with_check` = `lower(email) = lower(auth.email()) OR is_platform_admin()`, which scopes **rows, not columns** — and `is_platform_admin()` reads `businesses.is_platform_admin`, a column its own holder was allowed to write. - [ ] **Original C5 evidence (retained, 2026-08-04).** This is **not a new finding**: C5 has been tracked as Severe since the original audit, and `C12` is its mirror image (`Purchases.jsx` never replenishes stock on receipt, so neither side of the inventory lifecycle maintains `products.stock`). What is new is only the server-side half of the proof — C5 was established by reading application code, and nobody had ruled out the database doing the work. It doesn't. See C5/C12 in `architecture/Technical-Debt.md` for the canonical entries; the detail below is the evidence, not a separate item.
  `POS.jsx` reduces stock only via `setProducts(...)` (`charge()` and `chargeCredit()`), which is React state owned by `BusinessDashboard.jsx` and re-seeded from the database by `loadProducts()` on every mount. So the decrease a cashier sees is cosmetic and is overwritten on the next page load. No client-side write touches `products.stock` on a sale: POS never calls `updateProduct`, and `stock_batches` (Stock.jsx transfer/adjust) is a separate mechanism not wired to sales. Corroborating: the inventory seam commit removed an `updateStock` that was dead and malformed — client-side stock persistence was clearly intended here and never worked.
  **Verified server-side, not assumed:** a `pg_trigger`/`pg_proc` query against the live `carehub` project returned **zero rows** — no trigger on `sales`/`products`/`stock_batches`/`stock_movements`, and no `public` function whose body even mentions stock. Nothing decrements `products.stock` anywhere.
  Consequences: `products.stock` is overstated by every unit ever sold; POS out-of-stock and low-stock badges, Inventory's stock/cost valuation totals, and the CareFind listing filter (`stock > 0`) are all computed from a number that only ever goes up. **Historical stock values cannot be reconstructed from `products` alone** — a fix going forward does not repair existing quantities, and any backfill would have to be derived from the `sales.items` JSON. Fix design is an open decision (trigger on `sales` vs. an RPC called by the sale repository); it also needs rules for held sales, Services-category lines, and whether stock may go negative.

Root cause, read from the two files rather than assumed: `PostCard.jsx:366-367` wraps a post's body in its own `<p style={{ whiteSpace: 'pre-wrap', ... }}>{renderMarkdown(post.content)}</p>`, and `renderMarkdown` (`social-feed/markdown.jsx:286`) itself emits a block-level `<p key={key++} style={{ margin: 0 }}>` per paragraph — so a multi-paragraph post nests `<p>` inside `<p>`. Neither file was touched by the permalink work (`PostCard` is only a *consumer* of the new hook's `cardProps`), so this is not a regression from it. The browser's HTML parser silently closes the outer `<p>` at the first inner one and starts a new paragraph, which is why the practical symptom is post bodies rendering with the wrong spacing rather than a crash. Fix is a markup change (make the outer wrapper a `<div>`, or have `renderMarkdown` return inline content when called from a context that already provides the block element) — left open because this task is documentation-only.
- [ ] **CareFind suite is intermittently flaky under parallel load (found 2026-08-24, not fixed).** Roughly 1-in-N runs, a different file each time, fails a test that passes cleanly in isolation — concentrated in the suites that mount whole route trees: `BackgroundRoutes.test.jsx`, `PostModalRoute.test.jsx`, `PostPage.test.jsx`. Cause: React Testing Library's `findBy*`/`waitFor` default to a 1000ms timeout, and a route-tree mount under `vitest`'s parallel workers loses that race when jsdom is contended by sibling test files — not a real async bug in the components. `PostPage.test.jsx` already raised two assertions to 5000ms during this work (`PostPage.test.jsx:129`, `:184`) after they were observed flaking; the same shape is plausible anywhere else a route tree mounts, just not yet individually caught. This matters more than the usual "flaky test" complaint because CI is being introduced separately (tracked elsewhere) — a suite that goes red at random on a schedule teaches people to re-run CI rather than read what it says, right as the project is trying to get people to trust it.
- [ ] **A delete that RLS silently filters out still reads as a success (CareFind, found 2026-08-25 while fixing the unchecked-error half of it, not fixed).** `usePostEngagement.js`'s `handleDeletePost` now inspects the write's `error` and runs the host aftermath (PostPage's `navigate('/feed')`, PostModalRoute's `close()`) only on a clean write, so a transport failure or a database error can no longer look like a successful delete. What that does **not** cover: PostgREST reports a `DELETE` that matched no rows as a plain success, so an RLS policy that merely filters the row out arrives as `error: null` with nothing to distinguish it from a real delete. In practice the client-side `.eq('user_id', user.id)` scoping means the reader can only reach this by deleting a post they do not own, which the UI never offers — but a future policy change (moderation, business-owned posts) could make it reachable. The fix is to have the delete return its rows (`.delete(...).select()`) and treat an empty array as a failure; deferred here because it changes the query shape and the delete fixtures in three suites, which is more than the error-path fix this was found inside of.
