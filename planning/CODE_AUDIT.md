# CareHub Code Audit

This document tracks architecture issues discovered during review.

## Critical

- [x] **C18 — RESOLVED IN PRODUCTION 2026-08-05. Privilege escalation: any business owner could make themselves a platform admin with one PATCH.** Found while checking whether the tracked `saveBizDetails` whitelist item was worth doing — it was, but not for the stated reason: the whitelist is client-side, and the server had no column protection at all. `businesses`' only general policy is `ALL` with `qual`/`with_check` = `lower(email) = lower(auth.email()) OR is_platform_admin()`, which scopes **rows, not columns** — and `is_platform_admin()` reads `businesses.is_platform_admin`, a column its own holder was allowed to write. Setting it leaves `email` unchanged, so the `with_check` still passed. One `PATCH /rest/v1/businesses?id=eq.<own id>` — the same endpoint Settings already calls — granted platform-admin, and every table's RLS ORs `is_platform_admin()`, so that meant read/write across all 19 businesses' clinical and financial data. **Proven, not assumed**, by impersonating an ordinary owner (`authenticated` + their own JWT) inside a rolled-back block: `is_platform_admin` f → t, `status` active → approved, `plan` → enterprise, 18 of 18 other businesses readable. Note the INSERT policy already guarded exactly this (`is_platform_admin = false AND status = 'pending'`) — the signup path was closed and the update path left open. Fixed with a `BEFORE UPDATE` trigger, `guard_business_privileged_columns()`, rejecting changes by non-platform-admins to `is_platform_admin`, `status`, `plan`, `plan_expires_at`, `parent_business_id`, `referring_agent_id`; service role and existing platform admins pass through. Re-verified with the same attack (all four variants now 42501) plus all four legitimate write paths (owner profile save, owner booking save, AdminDashboard status change, service-role plan expiry) still working. SQL, full evidence and the one bug the verification caught in the trigger itself: `apps/carehub/sql/20260805_guard_business_privileged_columns.sql`.
- [x] **C5 — RESOLVED IN PRODUCTION 2026-08-04.** A `sale_stock_movement` trigger (`AFTER INSERT ON sales`) now decrements `products.stock` per line item of every completed sale, and `increment_product_stock()` makes Purchases' replenishment atomic. Both `SECURITY INVOKER` with pinned `search_path`; applied as tracked migrations. Verified in production inside a rolled-back `DO` block: 6500 → 6497 on a completed sale of qty 3, unchanged on a held sale, no residue. Canonical entry and full detail in `architecture/Technical-Debt.md` (C5, C12); SQL and verification notes in `apps/carehub/sql/20260804_sale_stock_movement.sql`. **Operational follow-up still outstanding:** existing quantities were deliberately NOT backfilled (35% of historical line items reference deleted products), so every business's stock is still overstated by everything sold to date until a physical count. The evidence trail that established the bug is retained below.
- [ ] **Original C5 evidence (retained, 2026-08-04).** This is **not a new finding**: C5 has been tracked as Severe since the original audit, and `C12` is its mirror image (`Purchases.jsx` never replenishes stock on receipt, so neither side of the inventory lifecycle maintains `products.stock`). What is new is only the server-side half of the proof — C5 was established by reading application code, and nobody had ruled out the database doing the work. It doesn't. See C5/C12 in `architecture/Technical-Debt.md` for the canonical entries; the detail below is the evidence, not a separate item.
  `POS.jsx` reduces stock only via `setProducts(...)` (`charge()` and `chargeCredit()`), which is React state owned by `BusinessDashboard.jsx` and re-seeded from the database by `loadProducts()` on every mount. So the decrease a cashier sees is cosmetic and is overwritten on the next page load. No client-side write touches `products.stock` on a sale: POS never calls `updateProduct`, and `stock_batches` (Stock.jsx transfer/adjust) is a separate mechanism not wired to sales. Corroborating: the inventory seam commit removed an `updateStock` that was dead and malformed — client-side stock persistence was clearly intended here and never worked.
  **Verified server-side, not assumed:** a `pg_trigger`/`pg_proc` query against the live `carehub` project returned **zero rows** — no trigger on `sales`/`products`/`stock_batches`/`stock_movements`, and no `public` function whose body even mentions stock. Nothing decrements `products.stock` anywhere.
  Consequences: `products.stock` is overstated by every unit ever sold; POS out-of-stock and low-stock badges, Inventory's stock/cost valuation totals, and the CareFind listing filter (`stock > 0`) are all computed from a number that only ever goes up. **Historical stock values cannot be reconstructed from `products` alone** — a fix going forward does not repair existing quantities, and any backfill would have to be derived from the `sales.items` JSON. Fix design is an open decision (trigger on `sales` vs. an RPC called by the sale repository); it also needs rules for held sales, Services-category lines, and whether stock may go negative.

## Refactoring

- [ ] `saveBizDetails` sends the entire `bizForm` object via generic PATCH — fine today, but consider a whitelist as the businesses table grows. **Re-scoped 2026-08-05:** checking this item is what surfaced **C18** (see Critical) — the server had no column protection whatsoever, so a client-side whitelist would have stopped nothing; the attack never goes through the app. C18's trigger is the real fix and is now live. This entry remains as a code-quality item only: `bizForm` is React state built from 12 known keys, and a field added for display would still be posted to the database. Low priority now that the privileged columns are guarded server-side.
- [x] **Deep repository seam — inventory pilot (2026-08-04).** `productRepository` is now a `createProductRepository(request = sbFetch)` factory: the transport (`sbFetch`, now exported from `services/supabase.js`) is an injected seam with two adapters — real PostgREST in prod, an in-memory adapter in `repositories/index.test.js` (10 tests). `Inventory.jsx` no longer imports `services/supabase` at all; every product read/write routes through the repository, which also enforces `business_id` tenant scoping on update/delete. Fixed two latent bugs uncovered in the process: (1) `productRepository.deleteBulk` was called by the duplicate-cleanup flow but never defined (would throw mid-cleanup, leaving a half-merged state); (2) `updateStock` was dead and malformed (unscoped PATCH with a non-PostgREST `{ increment }` body) — removed.
- [x] **Deep repository seam — expenses (2026-08-04).** Migrated `Expenses.jsx` fully off `services/supabase` onto a new `modules/expenses/repositories` (`createExpenseRepository(request = sbFetch)`, 5 in-memory-adapter tests). The in-memory adapter is now a shared test helper at `src/test/inMemoryClient.js` (the reusable second adapter — two concrete adapters make the transport seam real). Removed the duplicate/misplaced `expenseRepository` that had been sitting unused inside `inventory/repositories`.
- [x] **Deep repository seam — orders (2026-08-04).** Migrated `Orders.jsx` onto `modules/orders/repositories` (`createOrderRepository({ request, upload, notify })`, 10 in-memory-adapter tests). The orders aggregate is the first one that owns *commands*, not just queries: `create()` writes the order plus its items/watchers/files, logs the `submitted` event and fans out the approval + copy notifications; `advance()` moves the status, logs the event and notifies the raiser plus watchers. So three collaborators are injected, not one — `request` (transport), `upload` (object storage) and `notify` (notification fan-out) — which is what makes the fan-out assertable without a network, a bucket or a notifications table. Deleted the half-written `hooks/useOrders.js` (placeholder cross-domain loads, never imported). `Orders.jsx` still imports `getStaff`/`getTerritories`/`getEnterpriseLocations` from `services/supabase` — cross-aggregate reads belonging to modules that have not adopted the seam yet, flagged in-file.
- [x] **Deep repository seam — clients (2026-08-04).** Migrated `Clients.jsx` fully off `services/supabase` onto `createClientRepository(request = sbFetch)` (8 in-memory-adapter tests). The pre-existing `clientRepository` here was speculative and drifted — it exposed a `delete` and prescription reads nothing called, and lacked the four per-client history reads the page actually uses — so it was rewritten to the aggregate the page needs: `getAll`/`create`/`update` plus `getSales`/`getAppointments`/`getDebts`/`getConsultations`. The history reads are modelled as part of the *client* aggregate (projections of one client's record), not the sales/appointments/debts collections, which stay with their own modules. Deleted the unused `hooks/useClients.js` (drifted duplicate of logic already in the page). Cross-tenant hardening in the same pass — see below.
- [x] **Deep repository seam — POS sales (2026-08-04).** Migrated `POS.jsx` onto `createSaleRepository({ request, offline, isOnline })` (11 tests), filling the last of the empty `repositories/hooks/components` scaffolding. `create()` now owns the online-vs-offline decision the page used to make inline, returning `{ queued, reason }` so the page reports what happened without re-deriving how it was decided. The offline queue became its own store (`all`/`push`/`replace`) with a localStorage adapter and an in-memory one — the second adapter is what makes both branches of `create()` and the whole sync path testable; the localStorage key is unchanged so sales already queued on a device still replay. `BusinessDashboard`'s two `syncOfflineSales` call sites moved to the repository. Also dropped a dynamic `import('../../services/supabase')` used mid-function in `collectCredit`.
- [x] **Bug fixed — partial offline sync destroyed unsynced sales (2026-08-04).** `syncOfflineSales` cleared the entire offline queue whenever *at least one* sale synced (`if (count > 0) clearOfflineQueue()`). A partial failure — say three of five accepted, two rejected — deleted the two that never reached the database. Real money, silently gone, on the offline path the counter depends on when the network is bad. Now only the sales that actually landed are removed; failures stay queued for the next sync. Two regression tests cover partial failure and total failure. Fixed in its own commit, separate from the refactor that moved the code, so the behaviour change is reviewable on its own.
- [x] **Deep repository seam — debts + purchases (2026-08-05).** Migrated as one unit because they were coupled: both called the shared `updateDebt`, and both repositories already existed but sat misplaced and unused inside `inventory/repositories`. New `modules/debts/repositories` (`createDebtRepository(request = sbFetch)`, 15 tests) and `modules/purchases/repositories` (`createPurchaseRepository(request = sbFetch)`, 6 tests). `recordUnderpayment` — the "an underpaid sale or purchase automatically creates a debt" rule — moved from `services/supabase.js` onto the debt aggregate where it belongs, contract unchanged (still never throws, so a failed debt write cannot undo a completed sale or purchase). `services/supabase.js` no longer has any debts or purchases functions at all.
- [x] **`updateDebt`/`updatePurchase` id-only PATCHes now scoped (2026-08-05, with the migration above).** `updateDebt` was the last id-only PATCH on a money table. Because it was shared by `Debts.jsx`, `POS.jsx` (credit collection) and `Purchases.jsx` (mark-paid), scoping it required migrating all three call sites at once — which is exactly why debts and purchases were paired. Both writes are now filtered by `id` **and** `business_id`, with regression tests asserting a cross-tenant update is a no-op and a sibling row in the same business is untouched. Same latent class as the removed `updateSale`/`updateClient`: ids came from business-scoped lists, so this was an exposure rather than a live leak.
- [x] **Duplicated debt-settlement lookup consolidated (2026-08-05).** `POS.collectCredit` and `Purchases.markPaid` each fetched *every* debt in the business and scanned it in JavaScript for the one raised by the sale/purchase being settled. Both now call `debtRepository.findOpenBySource(source, sourceRef, businessId)`, which filters by business, source and source_ref in the query. The "not settled" test is deliberately kept in JavaScript rather than pushed into SQL as `status=neq.paid`: PostgREST would drop rows whose `status` is NULL (three-valued logic) where the previous `d.status !== 'paid'` matched them, and a missed debt there would leave a real balance standing after its source was marked paid. Covered by a regression test.
- [x] **Deep repository seam — reports (2026-08-05).** `Reports.jsx` now imports nothing from `services/supabase`. It deliberately gets **no repository of its own**: it owns no table, it is a read-only projection over three aggregates other modules own, so it composes `saleRepository`/`expenseRepository`/`purchaseRepository` instead. A `reportRepository` would have been an abstraction over nothing and a fourth copy of the same three queries. No new tests — no new logic was written, and the three methods it calls were already covered by their own modules' suites.
- [x] **`getSales`/`getTodaySales`/`getExpenses`/`addExpense`/`deleteExpense` retired (2026-08-05).** Retiring the sales reads meant repointing the two other callers, so `DashboardHome.jsx` and `Locations.jsx` had their sales reads moved onto `saleRepository.getAll`/`getToday` (those two modules are otherwise still unmigrated — this was a repoint, not a migration). Found while doing it: `Locations.jsx` imported `getSales` and never called it, and `addExpense`/`deleteExpense` had been **dead since the expenses migration** — `deleteExpense` was also an id-only DELETE with no business filter, the same unscoped-write class as the removed `updateStock`/`updateClient`. All five deleted.
- [ ] **`addSale` deliberately left in `services/supabase.js`.** `PharmacyForm.jsx` (consultation, unmigrated) is its only caller, and `saleRepository.create` is **not** a drop-in replacement: it parks failed or offline writes on the offline queue for later replay, which is right for a till but would silently change behaviour for consultation dispensing. Route it through the repository when `consultation` adopts the seam, as a deliberate decision rather than a side effect.
- [x] **Deep repository seam — appointments (2026-08-05).** `createAppointmentRepository(request = sbFetch)`, 9 in-memory-adapter tests. Both writes were unscoped in `services/supabase.js`: `updateAppointment` filtered on id alone, and `deleteAppointment` was an id-only DELETE — destructive, permission-gated behind a confirm dialog the page describes as permanent, and the most consequential unscoped write this rollout has found so far. Both now scoped by `business_id`, with regression tests asserting a cross-tenant update and a cross-tenant delete are each a no-op. The repository deliberately does **not** filter by `source`: CareFind books into this same table with `source: 'carefind'`, and those rows must stay visible — covered by a test.
- [x] **`dashboard-home` is now fully off `services/supabase` (2026-08-05).** Not a migration in its own right — it owns no table. Repointing its sales reads (with `reports`) and now its appointments read left it composing `saleRepository` + `appointmentRepository` and importing nothing from the service module. Same consumer shape as `reports`.
- [x] **Deep repository seam — stock (2026-08-05).** `createStockRepository({ request })`, 19 in-memory-adapter tests — the largest aggregate migrated so far. It owns `stock_batches`, the `stock_movements` journal, and the two multi-step *commands* (`transfer`, `adjust`) that were previously loose functions callers had to assemble correctly. The journal is deliberately **not** an injected collaborator (unlike `orders`' `upload`/`notify`): it is the same database through the same transport and part of this aggregate, so writing a batch change without its movement row is not an option any caller is given. `updateStockBatch` and `deleteStockBatch` were both unscoped (id-only PATCH, id-only DELETE); both are now scoped with cross-tenant regression tests. Thrown validation messages are rendered straight into toasts, so they are preserved verbatim and asserted.
- [x] **Ownership overlap on `stock_batches` resolved (2026-08-05).** `productRepository` carried `getStockBatches`/`addStockBatch` reaching into a table the stock module owns — with **zero callers, zero test coverage, and a different ordering** (`expiry_date.asc.nullslast`) than the functions the app actually used (`created_at.desc`). Removed. This is the overlap that made `stock` the right next unit rather than `settings`.
- [ ] **`stock_movements` is written but never read — half-built audit trail.** Every transfer and adjustment journals a row (batch, from/to location, signed quantity, reason, who) and **nothing in the app has ever surfaced it**. `getStockMovements` was the only reader-side function and had no callers, so it was not carried into the repository — adding a read method no screen calls would have made the repository speculative, the exact mistake the clients migration had to undo. Needs a product decision: build the movement history view (the data is already there and complete), or stop writing it. Do not quietly delete the writes — the journal is the only record of who moved or corrected stock.
- [x] **Stock transfer and adjustment are now atomic — RESOLVED IN PRODUCTION 2026-08-05.** `transfer_stock_batch()` and `adjust_stock_batch()`, both `SECURITY INVOKER` with pinned `search_path`, applied as tracked migrations (`atomic_stock_transfer`, `atomic_stock_adjustment`, plus `restrict_stock_batch_rpcs_to_authenticated` for the ACL). Three defects closed at once: (1) the partial-transfer path was two client-issued writes with no transaction, so a failed destination insert debited the source and lost the stock outright, with the movement row written last so nothing recorded the loss; (2) the quantity check ran in JavaScript against a possibly-stale read, so two users could both pass it on the same batch — now a `SELECT … FOR UPDATE` serialises them; (3) `adjust` journalled `newQty - batch.quantity` computed on the client, so a stale page could record a difference that never happened — now derived server-side from the locked row. Verified in production inside a `DO` block that raised at the end so it rolled back (confirmed after: still 1 batch, 0 movements, no residue): a 30-of-100 split conserved the total, an over-transfer was refused against the **current** quantity of 70 rather than the stale 100, a cross-tenant call returned NULL, and adjust journalled exactly −6. Advisors identical to the 27-finding baseline. SQL, full results and re-verification queries in `apps/carehub/sql/20260805_atomic_stock_transfer.sql`.
- [x] **Split batches no longer lose their costing (2026-08-05, with the above).** The old split copied 11 columns onto the destination batch and silently dropped four that exist on the table — `notes`, `cost_price`, `selling_price`, `sales_unit` — so a split half came back with cost_price 0 / selling_price 0 and no unit. All four now follow the stock. Measured before changing it: of the 1 live batch, 0 had a non-zero cost_price, 0 a selling_price, 0 a sales_unit and 0 notes, so the correction is inert on existing data and could not alter a row. It matters as soon as the receive form starts capturing those fields.
- [x] **Deep repository seam — warehouses (2026-08-05).** `createWarehouseRepository(request = sbFetch)`, 15 tests, over `enterprise_locations`. `updateEnterpriseLocation`/`deleteEnterpriseLocation` were both unscoped (id-only PATCH, id-only DELETE) and are now filtered by `business_id`, which matters more than usual here: four foreign keys point at this table. Chosen as the unit because it retires a genuinely **shared** read rather than just moving calls — both cross-aggregate readers (`Stock`, for which warehouse a batch sits in, and `Orders`, for which location an order is raised for) are repointed, so all four functions are deleted from `services/supabase.js` and Orders' flagged residual shrinks to `getStaff`/`getTerritories`. Not to be confused with `getAllLocations`/`getBranches`/`addBranch`, which are the multi-branch `businesses` tree and stay put.
- [x] **Unreadable delete error on warehouses fixed (2026-08-05, own commit).** Deleting a location still referenced by stock, orders or movement history is correctly refused by the database, but the raw Postgres foreign-key violation went straight into a toast. The repository now maps the **constraint name** (a stable schema object, unlike the violation's prose) to a readable reason — "still holds stock. Transfer or remove its batches first." and so on — and rethrows anything unrecognised untouched, so a network error is never flattened into a confident, wrong explanation. Behaviour fix kept in its own commit, separate from the refactor that moved the code.
- [ ] **A warehouse that has ever received a transfer can never be deleted.** `stock_movements.from_location_id`/`to_location_id` are foreign keys to `enterprise_locations` with no cascade, and the movement log is an append-only audit trail nothing ever deletes — so once a location appears in it, the row is permanent. Retiring a closed warehouse is a legitimate operation with no path today. Currently inert (0 movements live), and it surfaced while writing the delete-failure messages above rather than from a report. Needs a product decision: soft-delete/archive flag on `enterprise_locations` (preferred — keeps the audit trail intact and honest), or `ON DELETE SET NULL` on the two movement FKs, which would silently blank the history's origin. Related to the open "`stock_movements` is written but never read" question.
- [x] **Deep repository seam — settings (2026-08-05).** `createSettingsRepository(request = sbFetch)`, 14 tests. `Settings.jsx` imports nothing from `services/supabase`. The upsert became a real one: `saveSettings` was a read-then-PATCH-or-POST, now a single request resolved by the database on `business_settings`' `UNIQUE (business_id)` — which also closes the race where two first-time savers both read "no row" and both inserted (the unique constraint meant the loser got a 409, so nothing was ever corrupted, but a save failed for no reason the user could act on). POS's receipt printer reads settings through the same repository.
- [x] **`saveBizDetails` whitelist done (2026-08-05) — but it is NOT the security fix; see C18.** `saveBusinessProfile` copies an explicit `BUSINESS_PROFILE_FIELDS` list, so a field added to `bizForm` for display cannot reach the database. Tested against privileged column names specifically. The `businesses` boundary is documented in-file: that table has no owning module, so the settings repository owns only what the Settings *page* may change (profile, booking config), while AdminDashboard keeps its own `updateBusiness` path for approval status.
- [ ] **Repository-seam rollout (Candidate 1) still pending for ~12 modules.** Fully off `services/supabase`: `inventory`, `expenses`, `clients`, `debts`, `purchases`, `reports`, `appointments`, `dashboard-home`, `settings`, `warehouses`. Own aggregate on the seam with a flagged cross-aggregate residual: `orders`, `pos`, `stock`. ~10 modules still import `services/supabase` directly. All module scaffolding is now either filled or deleted.
- [ ] **`getClients` is still a shared `services/supabase` read despite `clients` owning a repository.** Called by `Debts.jsx` and `POS.jsx` as a cross-aggregate read; `clientRepository.getAll` is the same query. Repoint both and delete the services copy — left out of the debts/purchases unit deliberately to keep that diff to one aggregate pair.
- [x] **Latent bug fixed — `orderRepository.advance` issued an unscoped PATCH (2026-08-04).** `advance()` filtered by neither id nor business, so one call would have rewritten the stage/note of **every** order in the table, across every tenant. Same class as the removed inventory `updateStock`. It was dead at the time (the live path used `services/supabase.advanceOrder`), so it was a landmine rather than a live bug — but the orders migration above wires this exact method to the live approve/reject/dispatch buttons, so it was fixed first: scoped by `id` + `business_id`, with a regression test asserting a sibling order is untouched and another asserting a cross-tenant `advance` is a no-op. While fixing it, `advance` also stopped using `return=minimal` — it now reads the PATCH's returned rows to decide whether anything actually moved, so a cross-tenant or missing order no longer writes a phantom `order_events` audit entry for a status change that never happened (and it drops a redundant `getById` round-trip).
- [x] **Unscoped client reads/writes removed (2026-08-04, with the clients migration).** Four functions in `services/supabase.js` filtered on an id alone, with no `business_id`: `updateClient` (a PATCH — same unscoped-write class as the removed inventory `updateStock`) and `getSalesByClient`/`getAppointmentsByClient`/`getDebtsByClient`. All four had zero callers once `Clients.jsx` migrated (`updateClient` was already dead — imported but never called), so all four were removed rather than left to be reused. The repository replacements scope by `client_id` **and** `business_id`; all four history tables carry `business_id` and every insert site in the app stamps it, verified before the filters were added. Not a live-leak fix: the ids came from a business-scoped client list, so the exposure was latent.
- [ ] **`getLatestConsultation`/`getConsultationsByClient` still filter on `client_id` alone.** Kept in `services/supabase.js` because POS still calls them (it has not adopted the seam). Same latent class as the reads removed above — POS only passes ids from its own business-scoped client list, so it is not leaking today. Give them a `businessId` when `pos` adopts the repository seam.
