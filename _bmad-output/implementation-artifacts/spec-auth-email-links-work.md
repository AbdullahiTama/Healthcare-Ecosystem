## Intent

**Problem:** CareFind's `email_verification` email is minted server-side via `admin.auth.admin.generateLink` (`type: 'signup'`), but the client fires the action with no `redirectTo`, so the link defaults to `https://carefind.app` (the app root). Clicking it drops the user on the marketing page with no "email verified" confirmation, no path forward, and no feedback if the link is stale. There is no dedicated verify landing page at all.

**Approach:** Add a public CareFind `/verify-email` page that consumes the verification tokens on load -- PKCE `?code=` exchange via `exchangeCodeForSession`, or implicit `#access_token` hash (auto-detected by supabase-js) -- and shows verified/expired/info states with a clear CTA. Point the `email_verification` action's `redirectTo` at that route from the client (`AuthContext.signUp`). Verification remains Supabase-owned: links stay minted server-side and the page only exchanges/observes, never hand-verifies.

## Boundaries & Constraints

**Always:** Auth must flow through Supabase Auth -- never hand-decode tokens or claim verification client-side. Links stay minted server-side (`authEmail.js`); no client-side `generateLink`. `redirectTo` must resolve to the app's real origin + route (`window.location.origin`, never hardcoded domains). `/verify-email` must be a public route (outside `RequireAuth`). The page needs loading, success, expired/error, and no-token states, responsive layout, and accessible labels with `role=alert` error regions. Request-side anti-enumeration stays intact (generic 200 in `auth-email.js`).

**Ask First:** None expected; if the `email_verification` link's `redirectTo` proves to be overridden or ignored by Supabase project settings, HALT to confirm before changing `authEmail.js` defaults.

**Never:** Do not weaken auth or bypass Supabase. Do not add client-only email sends or move link generation to the browser. Do not touch `password_reset`/`ResetPassword.jsx` in this spec -- CareFind reset PKCE hardening is deferred (`_bmad-output/implementation-artifacts/deferred-work.md`). Do not change CareHub. Do not alter shared-email outbox behavior.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Signup with confirmation enforced | Email+password submitted, `data.session` null | `email_verification` email sent, link resolves to `{origin}/verify-email`; Login shows its "Check your email" screen | N/A |
| Click verify link -- implicit flow | `/verify-email#access_token=...&type=signup` | supabase-js auto-detects hash session; page shows "Email verified" + CTA | Invalid/expired token -> expired state with CTA; never false success |
| Click verify link -- PKCE flow | `/verify-email?code=...` | `exchangeCodeForSession` on mount; success -> "Email verified" + CTA | Exchange error -> expired/error state |
| Open `/verify-email` with no tokens | Plain GET, no code/hash, no session | Info state "Missing verification link" + back-to-login CTA | N/A |
| Already-verified user clicks a fresh verify link | User re-verified, has session | Success/verified state shown (session present) | N/A |

## Design Notes

PKCE vs implicit: supabase-js auto-processes callback URLs at `createClient()` init when `detectSessionInUrl` is left at its default `true` -- it auto-detects the implicit `#access_token`/`type=signup` hash (then clears `window.location.hash`) AND auto-exchanges a PKCE `?code=` when a stored code verifier exists for it (same browser that initiated the flow). That is exactly why the page must capture its URL auth params at module-import time (before the client consumes them) and must accept the arriving supabase session event as this link's verified verdict for a captured token-bearing URL; an explicit `exchangeCodeForSession` is only the fallback when a captured `?code=` exists but the client did not auto-handle it (cross-device, no stored verifier). CareHub's `ResetPassword.jsx` demonstrates the safe read-code -> exchange-guarded sequence, but it runs inside a client that also auto-processes the URL, so the import-time capture is the additional requirement here.

Consumption shape governs adjudication: on implicit success supabase-js clears the ENTIRE `window.location.hash` (auth-js `_getSessionFromURL` then `window.location.hash = ''`), and the implicit callback must carry `access_token`, `expires_in`, `refresh_token` and `token_type` or the client throws "No session defined in URL" (a minted `generateLink` `signup` link always carries all four plus `type`). On PKCE success the client strips only `code` (and the stored verifier) from the query. The page's visit record therefore derives the consumed URL as: implicit -> snapshot URL with hash dropped wholesale (branch-3 replays `verified` when the current bare URL matches); PKCE -> snapshot URL with `code` stripped (branch-3 replays when the current query matches). A genuinely different token URL, or a bare no-token open with no prior verdict, adjudicates fresh. Announce verdicts exactly once: move focus to the result heading with a visible outline (this announces) OR use a live region -- never both; the expired region may keep `role="alert"`.

> Iteration-2 note: the bare `getSession()`-then-`setSessionReady(!!session)` golden example below is NOT sufficient here -- it would restore the false-success bug. When reading session state on this page, require the session's `access_token` to match the hash's own `access_token` to prove *this link's* verification.

Golden example (CareHub reset init, `apps/carehub/src/pages/auth/ResetPassword.jsx:21-59`):
```js
const code = url.searchParams.get('code') || new URLSearchParams(url.hash.replace(/^#/, '?')).get('code')
if (code) { try { await authClient.auth.exchangeCodeForSession(window.location.href) } catch (e) { console.warn(...) } }
const { data } = await authClient.auth.getSession()
setSessionReady(!!data?.session)
```
